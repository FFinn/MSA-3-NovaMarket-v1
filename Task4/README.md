# Обоснование конфигураций NGINX

## Ограничение частоты запросов

В исходной конфигурации одна зона с лимитом `100r/s` применялась к вебу и мобильному приложению одновременно. В `rate-limiting.conf` общий маршрут `/api/` сохранён, но для него применяются три зоны:

- веб-канал — `50r/s` с IP;
- мобильный канал — `30r/s` с IP;
- неопознанный канал — защитный лимит `30r/s` с IP.

Канал определяется заголовком `X-Client-Channel`, который шлюз заполняет после успешной аутентификации по доверенному API-ключу или claim токена. Входящий одноимённый заголовок клиента должен быть удалён до этой точки. Нельзя основывать лимит на `User-Agent` либо позволять клиенту самостоятельно задавать канал: их можно подменить. За счёт пустого ключа в `limit_req_zone` на каждом запросе учитывается только одна зона. `burst` разрешает короткий всплеск, а `nodelay` не создаёт долгую скрытую очередь и после исчерпания лимита возвращает `429`.

## Защита вызовов к логистике

В NGINX с открытым исходным кодом нет полноценного Circuit Breaker с общим состоянием `closed/open/half-open` и строгой семантикой «пять **подряд** ошибок любого вида». Конфигурация реализует его базовый инфраструктурный вариант для upstream:

- `proxy_connect_timeout`, `proxy_send_timeout` и `proxy_read_timeout` — по три секунды;
- `max_fails=5 fail_timeout=30s` — после пяти неуспешных попыток связи, тайм-аутов или некорректных ответов в периоде `30s` основной upstream исключается на 30 секунд;
- после паузы NGINX снова направляет к нему запрос: это приближение проверки восстановления;
- при ошибке возвращается контролируемый JSON `503` и `Retry-After: 30`.

Ответы HTTP `500–504` направляются в fallback, но сами по себе не увеличивают счётчик `max_fails` в NGINX OSS. Для строгого требования «пять подряд ошибок, включая HTTP 5xx» необходим Circuit Breaker в коде вызывающего сервиса либо инфраструктурное решение с собственным состоянием: Envoy/Istio, NGINX Plus или OpenResty/Lua.

Резервный адрес `127.0.0.1:65535` нужен из-за особенности NGINX OSS: если в upstream только один `server`, `max_fails` не исключает его из балансировки. Резервный адрес быстро завершает соединение ошибкой, после чего клиент получает fallback-ответ.
