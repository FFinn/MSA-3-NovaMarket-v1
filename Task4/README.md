# Обоснование конфигураций NGINX

## Rate Limiting

В исходной конфигурации один zone с лимитом `100r/s` обслуживал оба канала, поэтому она не выполняла требования. В `rate-limiting.conf` используются две независимые зоны по `$binary_remote_addr`:

- `/api/web/` — 50 запросов в секунду с IP;
- `/api/mobile/` — 30 запросов в секунду с IP.

`burst` разрешает короткий контролируемый всплеск, `nodelay` не создаёт скрытую очередь и быстро возвращает `429` после исчерпания лимита. Для авторизованного API в промышленной конфигурации разумнее лимитировать по проверенному API-ключу или user id на шлюзе: IP может быть общим для нескольких пользователей.

## Circuit Breaker

NGINX Open Source не реализует полноценное общее состояние `closed/open/half-open` и строгую семантику «пять подряд» для произвольного внешнего URL. Здесь реализована предусмотренная заданием базовая инфраструктурная форма для `upstream`: `max_fails=5 fail_timeout=30s` временно исключает сбойный upstream; после паузы NGINX снова пробует направить к нему запрос.

Тайм-ауты подключения, отправки и чтения ограничены тремя секундами. Неработающий upstream и ответы `502–504` преобразуются в контролируемый fallback `503` с `Retry-After: 30`. Если нужна строгая модель с метриками процента/серии ошибок и централизованным состоянием, следует применить Envoy/Istio, NGINX Plus либо Circuit Breaker в коде вызывающего сервиса.
