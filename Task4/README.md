# Обоснование конфигураций NGINX

## Rate Limiting

В исходной конфигурации один zone с лимитом `100r/s` обслуживал оба канала, поэтому она не выполняла требования. В `rate-limiting.conf` используются две независимые зоны по `$binary_remote_addr`:

- `/api/web/` — 50 запросов в секунду с IP;
- `/api/mobile/` — 30 запросов в секунду с IP.

`burst` разрешает короткий контролируемый всплеск, `nodelay` не создаёт скрытую очередь и быстро возвращает `429` после исчерпания лимита. Для авторизованного API в промышленной конфигурации разумнее лимитировать по проверенному API-ключу или user id на шлюзе: IP может быть общим для нескольких пользователей.

## Circuit Breaker

NGINX Open Source не реализует полноценное общее состояние `closed/open/half-open` и строгую семантику «пять подряд» для произвольного внешнего URL. Здесь используется базовая инфраструктурная форма для `upstream`: `max_fails=5 fail_timeout=30s` временно исключает сбойный upstream; после паузы NGINX снова пробует направить к нему запрос.

В конфигурации добавлен `backup`-сервер `127.0.0.1:65535`. Он нужен из-за ограничения NGINX OSS: если в группе только один `server`, параметры `max_fails` и `fail_timeout` не дают ожидаемого отключения. Когда основной логистический endpoint временно исключён, backup быстро возвращает ошибку соединения, а клиент получает fallback.

Тайм-ауты подключения, отправки и чтения ограничены тремя секундами. Неработающий upstream и ответы `502–504` преобразуются в контролируемый fallback `503` с `Retry-After: 30`. Если нужна строгая модель с процентом ошибок, общей памятью состояния и полноценным half-open режимом, лучше применить Envoy/Istio, NGINX Plus либо Circuit Breaker в коде вызывающего сервиса.
