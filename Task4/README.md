# Обоснование конфигураций NGINX

## Ограничение частоты запросов

В исходной конфигурации одна зона с лимитом `100r/s` применялась к вебу и мобильному приложению одновременно. В `rate-limiting.conf` общий маршрут `/api/` сохранён, но для него применяются три зоны:

- веб-канал — `50r/s` с IP;
- мобильный канал — `30r/s` с IP;
- неопознанный канал — защитный лимит `30r/s` с IP.

Перед NGINX расположен доверенный компонент аутентификации. Он проверяет API-ключ или поле токена, удаляет входящий `X-Client-Channel` клиента и заново устанавливает `X-Client-Channel: web` либо `mobile`. Поэтому в эту конфигурацию попадает только подтверждённый признак канала. Это обязательное условие работы конфигурации: клиент не должен иметь возможность передать данный заголовок напрямую. Нельзя основывать лимит на `User-Agent` либо позволять клиенту самостоятельно задавать канал: их можно подменить. За счёт пустого ключа в `limit_req_zone` на каждом запросе учитывается только одна зона. Параметры `burst` и `nodelay` не используются: после исчерпания лимита NGINX возвращает `429`, не пропуская кратковременный избыток запросов.

## Защита вызовов к логистике

Конфигурация реализует инфраструктурный вариант Circuit Breaker для upstream:

- `proxy_connect_timeout`, `proxy_send_timeout` и `proxy_read_timeout` — по три секунды;
- `zone logistics_backend_state 64k` — состояние upstream общее для всех worker-процессов NGINX;
- `max_fails=5 fail_timeout=30s` — после пяти неуспешных попыток за период `30s` основной upstream исключается на 30 секунд; виды неуспешных попыток заданы в `proxy_next_upstream` (ошибка связи, тайм-ауты и `HTTP 500–504`);
- после паузы NGINX снова направляет к нему следующий запрос — это проверка восстановления;
- при ошибке возвращается контролируемый JSON `503` и `Retry-After: 30`.

`proxy_next_upstream_tries 1` не создаёт скрытых повторов: одна клиентская попытка соответствует одной попытке к логистике. Для более сложных политик, например отдельных порогов для разных кодов или адаптивного окна, потребуется Circuit Breaker в коде вызывающего сервиса либо инфраструктурное решение с расширенным состоянием.

Резервный адрес `127.0.0.1:65535` нужен из-за особенности NGINX OSS: если в upstream только один `server`, `max_fails` не исключает его из балансировки. Резервный адрес быстро завершает соединение ошибкой, после чего клиент получает резервный ответ.
