# Обоснование конфигураций NGINX

## Rate Limiting

В исходной конфигурации одна зона с лимитом `100r/s` применялась к вебу и мобильному приложению одновременно. Поэтому лимиты из задания она не выполняла. В `rate-limiting.conf` заведены две отдельные зоны по `$binary_remote_addr`:

- `/api/web/` — 50 запросов в секунду с IP;
- `/api/mobile/` — 30 запросов в секунду с IP.

`burst` разрешает короткий всплеск, а `nodelay` не копит длинную очередь и сразу возвращает `429`, когда лимит закончился. В боевой системе лучше лимитировать не только по IP, а по проверенному API-ключу или user id на шлюзе: один IP может быть общим для нескольких пользователей.

## Circuit Breaker

В NGINX Open Source нет полноценного общего состояния `closed/open/half-open` и строгой проверки «пять ошибок подряд» для любого внешнего URL. Здесь используется базовый вариант на `upstream`: `max_fails=5 fail_timeout=30s` временно исключает сбойный сервер; после паузы NGINX снова пробует отправить ему запрос.

В конфигурации добавлен резервный сервер `127.0.0.1:65535`. Он нужен из-за ограничения NGINX OSS: если в группе только один `server`, параметры `max_fails` и `fail_timeout` не дают ожидаемого отключения. Когда основной адрес логистики временно исключён, резервный адрес быстро возвращает ошибку соединения, а клиент получает запасной ответ.

Тайм-ауты подключения, отправки и чтения ограничены тремя секундами. Ошибки внешнего сервиса и ответы `502–504` переводятся в понятный ответ `503` с `Retry-After: 30`. Если нужна строгая модель с процентом ошибок, общей памятью состояния и полноценным half-open режимом, лучше вынести это в Envoy/Istio, NGINX Plus или в код вызывающего сервиса.
