# Обоснование конфигураций NGINX

## Ограничение частоты запросов

В исходной конфигурации одна зона с лимитом `100r/s` применялась к вебу и мобильному приложению одновременно. В `rate-limiting.conf` общий маршрут `/api/` сохранён, но для него применяются три зоны:

- веб-канал — `50r/s` с IP;
- мобильный канал — `30r/s` с IP;
- неопознанный канал — защитный лимит `30r/s` с IP.

Перед этим NGINX расположен доверенный компонент аутентификации. Он проверяет API-ключ или поле токена, удаляет входящий `X-Client-Channel` клиента и заново устанавливает `X-Client-Channel: web` либо `mobile`. Поэтому в эту конфигурацию попадает только подтверждённый признак канала. Нельзя основывать лимит на `User-Agent` либо позволять клиенту самостоятельно задавать канал: их можно подменить. За счёт пустого ключа в `limit_req_zone` на каждом запросе учитывается только одна зона. `burst` разрешает короткий всплеск, а `nodelay` не создаёт долгую скрытую очередь и после исчерпания лимита возвращает `429`.

## Защита вызовов к логистике

Конфигурация реализует инфраструктурный вариант Circuit Breaker для upstream:

- `proxy_connect_timeout`, `proxy_send_timeout` и `proxy_read_timeout` — по три секунды;
- `max_fails=5 fail_timeout=30s` — после пяти подряд неуспешных попыток за период `30s` основной upstream исключается на 30 секунд; виды неуспешных попыток заданы в `proxy_next_upstream` (ошибка связи, тайм-ауты и `HTTP 500–504`);
- после паузы NGINX снова направляет к нему следующий запрос — это проверка восстановления;
- при ошибке возвращается контролируемый JSON `503` и `Retry-After: 30`.

`proxy_next_upstream_tries 1` не создаёт скрытых повторов: одна клиентская попытка соответствует одной попытке к логистике. Для более сложных политик (например, отдельные пороги для разных кодов или адаптивное окно) потребуется Circuit Breaker в коде вызывающего сервиса либо инфраструктурное решение с расширенным состоянием.

Резервный адрес `127.0.0.1:65535` нужен из-за особенности NGINX OSS: если в upstream только один `server`, `max_fails` не исключает его из балансировки. Резервный адрес быстро завершает соединение ошибкой, после чего клиент получает fallback-ответ.
