# ADR-001: История покупок через CQRS read model и Customer BFF

- **Статус:** принято
- **Дата:** 2026-08-13
- **Контекст:** Task2 проектной работы NovaMarket

## Контекст и проблема

После доставки покупатель должен быстро видеть список всех заказов и детали каждого из них: товары, количества, цены на момент покупки, общую сумму, доставку, оплату, итоговый статус, чек, повтор заказа и отзыв. Данные принадлежат нескольким сервисам: заказам, каталогу, оплате, доставке и чекам. В будущем те же данные будут нужны веб-сайту, чат-боту и умным ассистентам.

### Функциональные требования

1. Покупатель видит только собственные заказы: список с датой, суммой и способом доставки; детали с составом заказа, ценами на момент покупки, оплатой и финальным статусом.
2. Для заказа доступны переход к скачиванию чека, начало сценария отзыва и повторного заказа.
3. История должна обновляться после событий оформления, оплаты, доставки, отмены и возврата без изменения контракта источников данных.
4. Новый клиентский канал использует тот же согласованный API истории и не интегрируется напрямую с доменными сервисами.

### Нефункциональные требования

1. Время ответа пользовательских операций: не более 0,3 с для p98 и не более 1 с для p99,99 при штатной нагрузке.
2. Масштабирование от 2 500 до 40 000+ заказов в день без линейного роста синхронных межсервисных вызовов на каждый экран.
3. История допускает eventual consistency: обновление проекции может отставать от доменного события; целевой lag — до 30 секунд, состояние «обновляется» должно быть прозрачно клиенту.
4. Доставка событий `at-least-once`; проекция должна быть идемпотентной и восстанавливаемой из Kafka.
5. Чтение истории не должно ухудшаться при недоступности каталога, оплаты или доставки.

## Решение

Выбираем **комбинацию CQRS и API Composition**:

1. `History Projection Service` подписывается на доменные события Kafka и формирует денормализованную read-модель `OrderHistory` в отдельной БД. В момент `OrderCreated` сохраняется неизменяемый снимок товарных позиций и цен — поэтому история не меняется при переименовании товара или новой цене в каталоге.
2. `Customer BFF` предоставляет клиентский контракт `GET /me/orders` и `GET /me/orders/{orderId}`. В штатном пути BFF читает историю одним запросом из read DB; для чека запрашивает/возвращает подписанную ссылку только при явном действии пользователя.
3. Владелец заказа остаётся источником истины для команд. BFF не изменяет заказы напрямую: «повторить», «отзыв» и скачивание чека запускают отдельные командные сценарии.
4. В обработчиках проекции используются `eventId`, номер версии и offset; повторное событие не меняет результат. Read DB можно пересобрать, проиграв события.

## Рассмотренные альтернативы

| Альтернатива | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Только API Composition: BFF синхронно вызывает Order, Catalog, Payment, Delivery | Быстрый старт, всегда самые свежие данные | N+1 и длинная цепочка HTTP-вызовов; высокая задержка, сильная связность и каскадные сбои; плохо укладывается в p98 0,3 с | Отклонена как основной путь |
| Только CQRS: клиент читает read DB напрямую | Быстрое чтение и независимое масштабирование | Клиент привязан к структуре read-модели; нельзя удобно развивать разный формат веба, чата и мобильного приложения | Отклонена |
| Event Sourcing для заказов и истории | Полный аудит и возможность восстановить состояние из событий | Существенно сложнее MVP: нужно проектировать агрегаты, версии событий, снапшоты, миграции и запросы; не нужен для решения именно экранов истории | Отложена; может быть введена для отдельных аудиторских доменов |
| Общая БД и SQL JOIN между сервисами | Простой запрос на старте | Нарушает автономность сервисов, создаёт общую точку отказа и блокирует независимое развитие | Отклонена |

## Последствия

### Положительные

- Предсказуемая низкая задержка: чтение выполняется из подготовленной проекции, без fan-out к доменным сервисам.
- Независимо масштабируются consumer проекции, read DB и BFF; новые подписчики Kafka не меняют существующие сервисы.
- Read-модель оптимизирована под пользовательский сценарий и индексы `(customer_id, ordered_at DESC)`.
- Сбой одного из сервисов-источников не делает историю недоступной: показывается последнее согласованное состояние.

### Отрицательные и меры

- Появляется eventual consistency. UI показывает статус синхронизации, а критически важная команда проверяет актуальное состояние в владельце агрегата.
- Больше компонентов и данных. Нужны мониторинг consumer lag, DLQ, outbox, алерты, схема событий и политика хранения.
- Данные дублируются. Это намеренная денормализация; за корректность отвечают события и повторяемая проекция.

## Контроль выполнения

- Нагрузочный тест проверяет p98/p99.99 endpoint истории отдельно от записи заказов.
- Метрики: latency BFF, ошибки, Kafka consumer lag, число событий в DLQ, скорость и ошибки проекции.
- Контракт событий версионируется (`eventVersion`); изменения проходят проверку совместимости.
