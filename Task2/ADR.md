# ADR-001. История покупок через CQRS-модель чтения и Customer BFF

### **Название задачи:**

Просмотр истории покупок в NovaMarket.

### **Автор:**

Александр Вафин.

### **Дата:**

2026-08-13.

### **Статус:**

Принято.

### **Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| 1 | Покупатель, клиентское приложение | Просмотреть список заказов | Покупатель открывает личный кабинет и видит свои заказы: дату оформления, сумму, способ доставки и итоговый статус. |
| 2 | Покупатель, клиентское приложение | Просмотреть детали заказа | Покупатель открывает заказ и видит товары, количество, цену на момент покупки, итоговую сумму, способ оплаты, способ доставки и финальный статус. |
| 3 | Покупатель, сервис чеков | Скачать чек | По явному действию покупателя система возвращает ссылку на чек. Чек не подгружается заранее для каждого заказа в списке. |
| 4 | Покупатель, Order Service, Review Service | Повторить заказ или оставить отзыв | Из деталей заказа покупатель запускает отдельный командный сценарий: повтор заказа или отзыв о товаре. История сама заказы не изменяет. |
| 5 | Доменные сервисы, History Projection Service | Обновить историю по событиям | История обновляется после событий заказа, оплаты, доставки, отмены и возврата. Источники событий не знают о новых клиентских каналах. |
| 6 | Мобильное приложение, сайт, чат-бот, ассистент | Получить единый клиентский API | Новый канал обращается к Customer BFF, а не собирает данные напрямую из сервисов заказов, каталога, оплаты и доставки. |

### **Нефункциональные требования**

| № | Требование |
| :-: | :- |
| 1 | Время ответа пользовательских операций: p98 не больше 0,3 секунды, p99,99 не больше 1 секунды при штатной нагрузке. |
| 2 | Решение должно масштабироваться от MVP с 2 500 заказами в день до 40 000+ заказов в день без роста числа синхронных межсервисных вызовов на один экран. |
| 3 | Для истории допускается согласованность с задержкой: проекция может отставать от доменного события до 30 секунд. Клиент должен видеть понятный статус, если данные ещё обновляются. |
| 4 | Доставка событий выполняется как минимум один раз. Обработчики проекции должны быть идемпотентными по `eventId`. |
| 5 | Недоступность каталога, оплаты или доставки не должна ломать чтение уже собранной истории покупок. |
| 6 | Проекцию нужно уметь восстановить повторным чтением событий из Kafka. |

### **Решение**

Выбрана комбинация **CQRS** и **API Composition**.

`History Projection Service` подписывается на события Kafka и собирает отдельную модель чтения `OrderHistory`. В неё входят заказ, позиции заказа, цены на момент покупки, способ оплаты, способ доставки, итоговый статус и ссылка на чек. При создании заказа сохраняется снимок товарных позиций и цен, поэтому история не меняется из-за переименования товара или новой цены в каталоге.

`Customer BFF` отдаёт клиентам методы `GET /me/orders` и `GET /me/orders/{orderId}`. В обычном сценарии BFF делает один запрос к базе модели чтения. За чеком он обращается к сервису чеков только по действию покупателя, чтобы не замедлять список заказов.

Источником истины для команд остаются доменные сервисы. Повтор заказа, отзыв и скачивание чека запускаются отдельными сценариями, а не меняют историю напрямую.

Для защиты от повторной доставки событий проекция хранит `eventId`, версию события и offset. Повтор события не должен менять результат. Если модель чтения потеряна, её можно пересобрать из Kafka.

Контейнерная диаграмма решения приложена в `c2-order-history-architecture.puml` и `c2-order-history-architecture.png`.

### **Альтернативы**

| Альтернатива | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Только API Composition: BFF синхронно вызывает Order, Catalog, Payment и Delivery | Быстрый старт, данные всегда свежие | Для экрана деталей появляется цепочка HTTP-вызовов. Задержка и риск каскадного сбоя растут вместе с числом сервисов. В p98 0,3 секунды уложиться сложно. | Отклонено как основной путь |
| Только CQRS: клиент читает модель чтения напрямую | Быстрое чтение, меньше промежуточных компонентов | Клиенты привязываются к структуре базы или внутреннего API проекции. Трудно развивать разные форматы для мобильного приложения, сайта и чат-бота. | Отклонено |
| Event Sourcing для заказов и истории | Полный аудит, состояние можно восстановить из событий | Для MVP это слишком сложный вариант: нужны версии событий, снимки агрегатов, правила миграции и отдельный подход к запросам. | Отложено |
| Общая база данных и SQL JOIN между сервисами | Просто на старте | Нарушает автономность сервисов, создаёт общую точку отказа, мешает независимому развитию команд. | Отклонено |

### **Недостатки, ограничения, риски**

1. История обновляется не мгновенно. Для покупателя это допустимо, но интерфейс должен показывать состояние обновления, если заказ только что изменился.
2. Появляется ещё один сервис и ещё одна база данных. Нужны метрики отставания consumer, DLQ, алерты и регламент восстановления проекции.
3. Данные дублируются. Это осознанная денормализация ради быстрого чтения. Корректность обеспечивают события, идемпотентные обработчики и возможность пересборки.
4. При изменении схемы событий требуется версионирование через `eventVersion` и проверка обратной совместимости.
