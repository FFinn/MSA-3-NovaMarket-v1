# ADR-001. История покупок через CQRS-модель чтения и Customer BFF

### **Название задачи:**

Получение агрегированных данных для сценария «Просмотр истории покупок» в NovaMarket.

### **Автор:**

Александр Вафин.

### **Дата:**

2026-08-13.

### **Статус:**

Принято.

### **Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| UC-01 | Покупатель, клиентское приложение | Просмотреть список заказов | Покупатель открывает личный кабинет и видит все свои заказы: дату оформления, сумму, способ доставки и итоговый статус. |
| UC-02 | Покупатель, клиентское приложение | Просмотреть детали заказа | Покупатель открывает заказ и видит товары, количество, цену на момент покупки, итоговую сумму, способ оплаты, способ доставки и конечный статус. |
| UC-03 | Покупатель, сервис чеков | Скачать чек | Покупатель нажимает «Скачать чек», после чего система выдаёт подписанную ссылку. При загрузке списка чек заранее не запрашивается. |
| UC-04 | Покупатель, Order Service | Повторить заказ | Из деталей истории покупатель создаёт новый заказ на основе сохранённого снимка позиций. Новый заказ проходит обычный сценарий резервирования и оплаты. |
| UC-05 | Покупатель, Review Service | Оставить отзыв | Покупатель из доставленного заказа создаёт отзыв о товаре. Review Service проверяет право на отзыв. |
| UC-06 | Доменные сервисы, History Projection Service | Обновить историю по событиям | После события заказа, оплаты, возврата, отмены или изменения статуса доставки read-модель обновляется. Источники событий не зависят от клиентских каналов. |
| UC-07 | Мобильное приложение, сайт, чат-бот, ассистент | Получить единый API истории | Новый канал обращается к Customer BFF и не собирает информацию напрямую из сервисов заказов, оплаты и доставки. |

### **Нефункциональные требования**

| № | Требование |
| :-: | :- |
| NFR-01 | Время ответа экранов истории: p98 не больше 0,3 секунды, p99,99 не больше 1 секунды при штатной нагрузке. |
| NFR-02 | Решение должно масштабироваться от 2 500 до 40 000+ заказов в день без линейного роста синхронных вызовов к доменным сервисам на каждый экран. |
| NFR-03 | Для истории допускается согласованность с задержкой: read-модель может отставать от доменного события до 30 секунд. Если данные ещё обновляются, клиент видит понятный статус. |
| NFR-04 | Доставка событий выполняется как минимум один раз. Обработчики проекции идемпотентны по `eventId`. |
| NFR-05 | При временной недоступности каталога, оплаты или доставки уже сформированная история покупок остаётся доступной. |
| NFR-06 | Проекция должна восстанавливаться повторным чтением событий из Kafka. |
| NFR-07 | Контракт событий должен быть версионирован (`eventVersion`) и обратно совместим для работающих потребителей. |

### **Решение**

Выбрана комбинация **CQRS** и **Customer BFF**. CQRS — основной паттерн: он даёт быстрый путь чтения через отдельную денормализованную модель. BFF предоставляет единый контракт для разных каналов и выполняет ограниченную композицию только для дополнительных действий, например выдачи ссылки на чек.

`History Projection Service` подписывается на события Kafka и строит отдельную модель чтения `OrderHistory` в `Order History Read DB`. Для списка и деталей заказа он использует снимок позиций, названий и цен из `OrderCreated`; последующие изменения текущей карточки товара не меняют историю покупки. События оплаты, возврата, отмены и `DeliveryStatusChanged` дополняют сведения об оплате, трек-номер, прогноз даты и финальный статус `delivered` или `cancelled`.

`Customer BFF` предоставляет `GET /me/orders` и `GET /me/orders/{orderId}`. В обычном сценарии он обращается к API чтения `History Projection Service`, которое читает готовую модель одним запросом. Поэтому отображение истории не зависит от доступности доменных сервисов. По действию пользователя BFF запрашивает в сервисе чеков короткоживущую подписанную ссылку.

Команды остаются у владельцев доменов: BFF вызывает Order Service для повтора заказа и Review Service для создания отзыва. Проекция истории не изменяет заказы и не становится источником истины.

Для надёжной обработки проекция хранит обработанные `eventId`, версию события и смещение Kafka. Потерянную read-модель можно пересобрать повторным чтением топиков. Контейнерная диаграмма приведена в `c2-order-history-architecture.puml`.

### **Альтернативы**

| Альтернатива | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Только API Composition: BFF синхронно вызывает Order, Catalog, Payment и Delivery | Быстрый старт, данные всегда свежие | Длинная цепочка HTTP-вызовов, высокая задержка и риск каскадного сбоя. Для p98 0,3 секунды решение ненадёжно. | Отклонено как основной путь |
| Только CQRS: клиент читает read-модель напрямую | Быстрое чтение, меньше компонентов между клиентом и данными | Клиент привязывается к внутреннему контракту; труднее развивать разные форматы мобильного приложения, сайта и чат-бота. | Отклонено |
| Event Sourcing для заказов и истории | Полный аудит, возможность восстановить состояние из событий | Для MVP избыточно: нужны снимки агрегатов, миграции и отдельный подход к запросам. | Отложено |
| Общая БД и SQL JOIN между сервисами | Простой запрос на старте | Нарушает автономность сервисов, создаёт общую точку отказа и мешает независимому развитию. | Отклонено |

### **Недостатки, ограничения, риски**

1. История обновляется не мгновенно. Для покупателя это допустимо, но интерфейс должен явно показывать состояние обновления, если заказ только что изменился.
2. Появляются дополнительный сервис и БД. Нужны метрики отставания потребителя Kafka, очереди неразобранных сообщений, оповещения и регламент восстановления проекции.
3. Данные дублируются. Это осознанная денормализация ради быстрого чтения; корректность обеспечивают события, идемпотентные обработчики и пересборка.
4. Изменение схемы событий требует обратной совместимости и контроля версий, иначе обновление проекции может остановиться.
